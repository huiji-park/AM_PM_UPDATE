# AM_PM MVP — 화면·검증 명세

- 작성일: 2026-10-03
- 버전: 0.2 / 제약 검토 보완, 사용자 검토용
- 상위 문서: [상세 설계](2026-10-03-am-pm-mvp-design.md)
- API 기준: [API 계약서](2026-10-03-am-pm-mvp-api-contract.md)

이 문서는 최종 디자인 시안이나 이미 실행한 테스트 보고서가 아니다. 개발할 화면의 동작과 완료 판단 기준을 정의한다. 색·간격은 제안 기본값이고 기능·권한·실패 동작은 계약이다.

## 1. 정보 구조·라우트

| 화면 ID | 경로 | 제목 | 접근 |
|---|---|---|---|
| S01 | /login | 로그인 | 공개, 로그인 상태면 /projects로 이동 |
| S02 | /register | 회원가입 | 공개, 로그인 상태면 /projects로 이동 |
| S03 | /projects | 내 프로젝트 | 로그인 |
| S04 | /projects/new | 프로젝트 만들기 | 로그인 |
| S05 | /projects/:projectId/tasks | 업무 | 프로젝트 소속 |
| S06 | /projects/:projectId/tasks/:taskId | 업무 상세 | 프로젝트 소속 |
| S07 | /projects/:projectId/members | 팀원 | 프로젝트 소속 |
| S08 | /projects/:projectId/settings | 프로젝트 설정 | 소유자 |
| S09 | 정의하지 않은 경로 | 페이지를 찾을 수 없습니다 | 공개 |

`/`는 인증 확인 후 /projects 또는 /login으로 이동한다. `/projects/:projectId`는 업무 탭으로 이동한다. /projects/new를 동적 프로젝트 ID보다 명시적으로 우선 정의한다.

보호 페이지로 직접 진입한 비로그인 사용자는 `next`에 내부 경로만 담아 로그인 화면으로 이동한다. next는 Vue Router가 해석한 허용된 앱 경로여야 한다. 외부 origin, `//host`, scheme, 역슬래시, /login·/register 루프는 거부하고 /projects를 사용한다.

로그인 성공 후 next로 이동하더라도 서버에서 소속을 다시 확인한다. 주소에 UUID가 있다고 프로젝트 존재를 보장하지 않는다.

### 1.1 전역 상태

| 상태 | 표시 | 허용 동작 |
|---|---|---|
| 인증 확인 중 | 로딩 영역, 보호 데이터 미표시 | 중복 초기화 요청 없음 |
| 인증됨 | 사용자 표시 이름·로그아웃·내 프로젝트 | 해당 권한의 페이지 |
| 비로그인 | 로그인·회원가입 | 공개 페이지 |
| 인증 확인 통신 실패 | ‘서버에 연결할 수 없습니다’ + 다시 시도 | 인증 재확인만 |

사용자가 로그인 버튼을 누를 때마다 별도 /auth/me 요청을 중복 전송하지 않는다. 로그인 응답의 User로 인증 상태를 갱신한다. 로그아웃 성공 후 모든 보호 데이터·검색 결과·편집 초안을 지운다. 브라우저 뒤로 가기로 이전 화면을 열어도 다시 인증·권한을 확인한다.

## 2. 기본 UI 규칙

### 2.1 레이아웃

데스크톱은 높이 64px 상단 헤더, 224px 프로젝트 내비게이션, 유동 본문으로 구성한다. 본문은 최대 1,440px, 기본 패딩 24px다. 768px 미만에서는 사이드바를 메뉴 버튼으로 접고 본문 패딩 16px를 사용한다. 폼은 최대 560px로 읽기 편한 너비를 유지한다.

프로젝트 화면의 상단은 이름, 설명 요약, 프로젝트 기간, 소유자, 전체 업무 완료율을 표시한다. 탭은 업무·팀원·설정이다. 일반 팀원에게 설정 탭을 표시하지 않는다. 업무 탭의 필터는 프로젝트 전체 집계 숫자를 바꾸지 않는다.

```text
┌ AM_PM                                      사용자 이름 · 로그아웃 ┐
│ 내 프로젝트 │ 프로젝트 이름                         새 업무      │
│             │ 기간 · 완료율 · 전체 업무 수                        │
│ 업무        │ 검색 [           ] 담당자 [전체] 상태 [전체]        │
│ 팀원        │ 마감일 [     ~     ] 지연만 [ ]  목록 | 보드         │
│ 설정*       │                                                    │
│             │ 업무 내용 / 페이지 또는 보드의 상태별 더 보기        │
└─────────────┴────────────────────────────────────────────────────┘
* 설정은 소유자만 표시
```

### 2.2 시각 기본값

| 토큰 | 값·정책 |
|---|---|
| 배경 | #F8FAFC, 카드·폼 #FFFFFF |
| 기본 글자 | #0F172A, 보조 #475569 |
| 강조 | #1D4ED8, 흰 글자 |
| 오류·삭제 | #B91C1C, 위험 동작에서만 사용 |
| 성공 | #166534 |
| 간격 | 4·8·12·16·24·32px 체계 |
| 모서리 | 카드 12px, 입력·버튼 8px |
| 본문 | 16px, 줄높이 1.5 이상, 시스템 한글 폰트 |
| 컨트롤 | 기본 높이 44px 이상 |

할 일·진행 중·완료는 배경색뿐 아니라 텍스트 배지로 구분한다. ‘지연’은 별도 텍스트와 아이콘을 함께 표시한다. 색 조합은 구현 후 실제 대비를 검사해 일반 텍스트 4.5:1 기준을 만족하도록 조정한다.

### 2.3 공통 컴포넌트

Button, FormField, TextInput, Textarea, Select, DateInput, Modal, ConfirmDialog, Toast, InlineAlert, EmptyState, LoadingSkeleton, Pagination, StatusBadge, UserSummary를 공통화한다. 기능별 API 호출은 공통 UI 컴포넌트 안에 넣지 않는다.

Modal은 제목·설명 연결, 열릴 때 포커스 이동, focus trap, Esc 닫기, 닫은 후 호출 버튼으로 포커스 복귀를 지원한다. 저장 중에는 닫기·중복 제출을 막는다. 제출 실패하면 첫 오류 필드로 포커스를 옮긴다. 오류를 toast에만 표시하지 않는다.

일반 toast는 약 4초 후 사라지되 닫기 버튼을 제공한다. 폼 오류·충돌·삭제 실패처럼 사용자의 조치가 필요한 메시지는 사용자가 처리할 때까지 유지한다. 모션은 최소화하고 prefers-reduced-motion을 존중한다.

## 3. S01 로그인

필드: 이메일, 비밀번호. 버튼: 로그인, 비밀번호 보기, 회원가입 링크. 비밀번호 보기 버튼은 현재 상태를 보조기술에 알린다. 이메일 자동완성은 username, 비밀번호는 current-password를 사용한다.

| 동작 | 동작 결과 |
|---|---|
| 로그인 제출 | 필드 검사 후 A02, 버튼을 ‘로그인 중’으로 변경 |
| 성공 | User 저장, 내부 next 또는 /projects로 이동 |
| 잘못된 자격증명 | ‘이메일 또는 비밀번호를 확인해 주세요’, 비밀번호 지우기 |
| 429 | 재시도 안내, Retry-After가 있으면 남은 시간 표시 |
| 서버·네트워크 오류 | 이메일 유지, 비밀번호는 메모리에서만 유지, 직접 재시도 |
| 회원가입에서 돌아옴 | 가입 성공 메시지와 이메일만 채우기 |

‘로그인 유지’ 체크박스는 제공하지 않는다. 세션은 모두 7일 절대 만료다. 비밀번호 찾기·소셜 로그인 버튼은 작동하지 않는 장식으로 넣지 않는다.

## 4. S02 회원가입

필드: 표시 이름, 이메일, 비밀번호, 비밀번호 확인. 비밀번호 제한은 입력 아래 ‘12~128자’로 항상 표시한다. 자동완성은 name, email, new-password를 사용한다.

서버 제출 전 비밀번호 일치·필드 형식을 검사한다. 비밀번호 확인은 API payload에서 제외한다. 가입 성공 후 모든 비밀번호 값을 지우고 /login으로 이동한다. 중복 이메일은 해당 필드에 오류를 표시한다. 실패 시 다른 필드 입력을 잃지 않는다.

이메일 인증을 구현한 것처럼 확인 메일 안내를 표시하지 않는다. MVP는 포트폴리오 시연용 계정 흐름이라는 범위를 README에 명시한다.

## 5. S03 내 프로젝트

헤더는 ‘내 프로젝트’, 검색창, 정렬 선택, ‘프로젝트 만들기’ 버튼이다. 카드는 프로젝트 이름, 설명 2줄, 기간 또는 ‘기간 미정’, 내 역할을 표시한다. 카드 이름 링크를 통해 업무 탭으로 이동한다.

| 화면 상태 | 문구·행동 |
|---|---|
| 최초 로딩 | 카드 skeleton, 중복 GET 취소 |
| 프로젝트 0개 | ‘첫 프로젝트를 만들어 보세요’ + 만들기 |
| 검색 결과 0개 | ‘검색 결과가 없습니다’ + 검색 초기화 |
| 조회 실패 | 이전 데이터가 있으면 오래된 데이터임을 표시, 다시 시도 |
| page 범위 초과 | 마지막 유효 페이지로 한 번 이동·재조회, total=0이면 page=1 |

검색·정렬·페이지를 URL에 유지한다. 검색어나 정렬이 바뀌면 page=1이다. 브라우저 뒤로 가기로 직전 검색 결과 위치를 복원한다. 카드별 집계 추가 호출은 하지 않는다.

## 6. S04 프로젝트 만들기

필드: 이름(필수), 설명, 시작일, 종료일. 날짜를 한쪽만 입력하면 나머지 필드 아래에 오류를 표시한다. 날짜를 입력하지 않고 생성할 수 있다. 제출 성공 후 새 프로젝트 업무 탭으로 이동한다.

소유자 입력은 없다. 현재 사용자가 소유자가 된다는 안내를 표시한다. 생성 실패 시 폼을 유지하고 목록에 가짜 프로젝트를 추가하지 않는다. 저장 요청 결과가 유실되면 목록 확인을 권한다.

폼이 변경된 상태에서 페이지 이동·모달 닫기를 시도하면 변경사항 버리기 확인을 한다. 성공 저장·명시적 취소 후에는 경고하지 않는다. 브라우저 종료 시 beforeunload 경고는 브라우저 지원 범위에서 제공하며 자동 저장을 약속하지 않는다.

## 7. S05 업무 목록·보드

### 7.1 공통 필터

검색, 담당자(전체·나·미배정·팀원 선택), 마감일 범위, ‘지연만 보기’, 정렬을 제공한다. 목록에서만 상태 필터를 제공한다. 보드로 바꾸면 단일 status query를 제거하고 세 열을 모두 표시한다. 보드에서 목록으로 돌아올 때 상태 기본값은 전체다.

UI의 ‘지연만 보기’는 체크 시 overdue=true, 해제 시 overdue 파라미터 생략이다. API의 overdue=false는 ‘지연 제외’ 의미지만 첫 버전 UI에는 별도 체크박스를 추가하지 않는다.

필터를 바꾸면 목록 page와 보드 열별 페이지를 초기화한다. view=list|board는 프론트 URL 상태이며 API에 전달하지 않는다. 보드의 `todo_pages`, `in_progress_pages`, `done_pages`는 각 열에서 표시 중인 페이지 수를 뜻하는 양의 정수 URL query이며 기본 1이다. 복원 시 해당 개수까지 순서대로 로드하되 API가 반환한 total_pages를 넘지 않는다. 이 query들도 API에 직접 전달하지 않는다. 화면 URL의 잘못된 view·페이지 값은 기본값으로 정규화한다. 선택된 담당자의 멤버십이 사라져도 현재 검색 필터 자체는 유지해 결과가 비었음을 알리고 초기화할 수 있게 한다.

### 7.2 목록

| 열 | 내용 |
|---|---|
| 제목 | 업무 상세 링크, 길면 말줄임·접근 가능한 전체 이름 |
| 상태 | 상태 배지와 변경 선택 |
| 담당자 | 표시 이름 또는 ‘미배정’ |
| 일정 | 시작일~마감일, 마감일만, 또는 ‘일정 미정’ |
| 지연 | 서버 is_overdue가 참일 때 텍스트 배지 |
| 작업 | 상세·편집, 권한 있을 때 삭제 |

모바일은 각 행을 카드로 바꾸고 전체 페이지의 가로 스크롤을 만들지 않는다. 상태 수정 시 task.version을 보내고 성공 후 현재 필터를 다시 조회한다. 수정 결과가 현재 필터와 맞지 않으면 행이 사라지고 ‘상태를 변경했습니다’ 메시지를 표시한다.

### 7.3 보드

TODO(할 일), IN_PROGRESS(진행 중), DONE(완료) 3열이다. 각각 status를 고정한 목록 API를 요청한다. 카드에 제목·담당자·마감일·지연 배지·상태 선택을 표시한다. 열의 숫자는 해당 열 API total로, 현재 검색·필터를 반영한다.

각 열은 처음 20개를 표시하고 ‘더 보기’로 20개씩 추가한다. 전체 업무를 무제한 한 번에 받지 않는다. 한 열 실패 시 그 열 안에 재시도 버튼을 표시하고 다른 열은 유지한다. 한 열의 로딩이 끝나기 전 0개라고 표시하지 않는다.

카드 상태 변경은 서버 성공 후에 화면을 갱신한다. 세 열 모두 페이지 1부터 이미 표시 중이던 페이지 수까지 다시 조회한다. 수신 결과의 같은 업무 ID는 가장 큰 version 하나만 남기고 그 응답의 status 열에 표시한다. 최신 total이 줄었으면 유효 페이지까지만 유지한다. 재조회 중에는 갱신 중임을 표시하며 프로젝트 요약 집계도 함께 갱신한다.

세 열·여러 페이지·전체 집계는 서로 다른 HTTP snapshot이다. 다른 사용자가 계속 변경하는 동안 일시적인 누락이나 숫자 차이는 있을 수 있다. 중복 표시를 제거하고, 쓰기가 멈춘 후 전체 재조회를 완료하면 최신 결과로 수렴한다. 실시간 동기화나 보드 전체의 원자적 snapshot을 보장한다고 표현하지 않는다. 한 열이 실패하면 기존 데이터와 갱신 실패 표시를 유지한다.

768px 미만은 보드 영역만 가로 스크롤하고 각 열 최소 너비 280px를 유지한다. 키보드로 세 열과 카드에 접근할 수 있어야 한다. 목록 전환을 항상 제공한다.

### 7.4 새 업무

‘새 업무’는 업무 생성 Modal을 연다. 필드는 제목, 설명, 상태, 담당자, 시작일, 마감일이다. 기본 상태 TODO, 담당자 미배정, 일정 미정이다. 담당자 선택은 M01을 페이지로 불러오고 소유자를 포함한다.

기본값으로 현재 사용자·프로젝트 기간을 자동 배정하지 않는다. 기간 밖의 일정은 경고문을 표시하되 저장 버튼을 막지 않는다. 저장 성공 시 Modal을 닫고 현재 목록·보드와 프로젝트 요약을 다시 조회한다.

현재 필터 때문에 새 업무가 보이지 않으면 성공 toast에 ‘업무 보기’ 링크를 제공한다. 생성된 업무를 보이게 하려고 사용자 필터를 몰래 초기화하지 않는다.

## 8. S06 업무 상세·수정

직접 URL 진입·새로고침 가능한 독립 화면이다. 제목, 상태, 담당자, 작성자, 일정, 설명, 생성·수정 시각, 완료 시각을 표시한다. 표시 시각은 Asia/Seoul로 변환하고 날짜 단위 일정은 그대로 보여준다.

모든 팀원에게 ‘수정’ 버튼이 있다. 소유자 또는 작성자에게만 ‘삭제’ 버튼이 있다. 담당자이지만 작성자가 아닌 팀원에게는 삭제를 표시하지 않는다.

수정 폼은 서버에서 읽은 version과 원본 스냅샷을 보관한다. 변경한 필드와 expected_version만 전송한다. 저장되지 않은 변경이 있으면 이동 확인을 한다. 설명은 텍스트와 줄바꿈으로 표시하고 HTML로 해석하지 않는다.

### 8.1 수정 충돌

409 VERSION_CONFLICT가 발생하면 기존 입력을 유지하고 저장을 중지한다. 최신 Task를 GET해서 다음 두 선택을 제공한다.

1. **최신 내용으로 다시 편집:** 내 초안 버리기를 확인한 뒤 최신 값을 폼에 넣는다.
2. **내 변경사항 검토:** 필드별 최신 값·내 수정값을 나란히 보여주고 사용자가 다시 적용할 필드를 선택한다. 명시적 ‘선택한 변경 저장’ 클릭 시 최신 version으로 요청한다.

자동 병합·자동 덮어쓰기는 없다. 다시 저장하는 사이 또 바뀌면 같은 충돌 절차를 반복한다. 팀원 제거로 담당자가 비워진 충돌에서는 제거된 사용자를 재선택할 수 없다.

GET이 404이면 삭제·권한 변경 안내로 바꾸고 저장을 금지한다. 401이면 초안을 지운다. 5xx·통신 오류라면 초안을 유지하고 재조회만 제공한다.

### 8.2 삭제

업무 제목과 ‘삭제한 업무는 복구할 수 없습니다’를 확인창에 표시한다. 삭제 성공 후 업무 목록으로 이동한다. 목록에서 열었던 경우 저장해 둔 같은 프로젝트의 query를 복원하고, 직접 진입이면 기본 목록으로 이동한다. 충돌이면 삭제하지 않고 최신 업무를 다시 확인하게 한다.

## 9. S07 팀원

팀원 목록은 표시 이름, 소유자·팀원 배지, 참여 날짜를 표시한다. 이메일은 보여주지 않는다. 현재 사용자는 ‘나’ 표시를 추가한다. 모든 팀원이 조회 가능하며 소유자에게만 ‘팀원 추가’, ‘제거’, ‘소유권 이전’을 표시한다.

### 9.1 팀원 추가

정확한 이메일 입력 Modal에서 ‘이미 가입된 사용자를 프로젝트에 바로 추가합니다’라고 안내한다. 제출 시 현재 ProjectDetail의 version을 사용한다. 전역 이메일 자동완성이나 사용자 검색은 없다.

대상 없음은 이메일 필드 안내, 중복은 이미 참여 중이라는 안내다. 성공하면 목록·프로젝트 상세를 갱신한다. 409 VERSION_CONFLICT면 입력 이메일을 보존하고 최신 프로젝트 버전을 불러온 뒤 사용자가 다시 제출해야 한다.

### 9.2 제거·탈퇴

제거 확인창: ‘이 사용자의 프로젝트 접근 권한이 사라집니다. 담당 업무는 미배정으로 바뀌며 업무 내용은 유지됩니다.’ 별도 담당 업무 개수 API를 추가하지 않는다.

일반 팀원에게는 ‘프로젝트 나가기’를 표시한다. 소유자에게는 ‘소유권을 이전한 후 나갈 수 있습니다’라는 안내를 표시한다. 탈퇴 성공 후 내 프로젝트 목록으로 이동한다.

제거·탈퇴는 project.version을 사용한다. 충돌이면 새 멤버 목록·역할을 확인한 후 다시 결정한다. 소유권을 잃었다면 관리 버튼을 즉시 숨긴다.

### 9.3 소유권 이전

현재 팀원 한 명을 선택하고 이름과 ‘이전 후 나는 일반 팀원이 됩니다’를 확인한다. 본인은 대상 목록에서 제외한다. 성공하면 역할·프로젝트 version을 갱신하고 일반 팀원 화면으로 전환한다.

소유권 이전과 팀원 삭제를 한 번에 묶는 UI는 만들지 않는다. 이전 사용자가 프로젝트에서 나가려면 별도로 탈퇴해야 한다.

## 10. S08 프로젝트 설정

이름·설명·시작일·종료일 수정 폼과 별도 위험 구역의 프로젝트 삭제를 제공한다. 일반 팀원이 URL로 직접 접근하면 프로젝트 데이터를 불필요하게 편집 폼에 채우지 않고 ‘설정을 변경할 권한이 없습니다’와 업무 탭 링크를 표시한다.

수정은 P04와 project.version을 사용한다. 충돌은 업무 수정과 동일하게 최신 값과 초안을 비교한다. 팀원 변경만으로도 project.version이 달라질 수 있으므로 충돌 안내에 특정 사람이 프로젝트 이름을 바꿨다고 단정하지 않는다.

삭제 확인창에는 프로젝트 이름, 하위 업무·팀원 관계가 함께 삭제된다는 설명, 이름 재입력 필드를 제공한다. 입력값이 현재 표시된 이름과 정확히 일치해야 버튼을 활성화한다. 서버가 버전 충돌을 반환하면 최신 프로젝트를 확인하고 이름을 다시 입력해야 한다.

삭제 성공 시 목록으로 이동한다. 현재 클라이언트에 로드된 해당 프로젝트의 모든 상태를 제거한다. 다른 사용자의 화면은 다음 요청에서 404를 받아 접근 불가 상태로 전환된다. 실시간으로 강제 이동시킨다고 약속하지 않는다.

## 11. 공통 오류·재조회 정책

| 상황 | 화면 정책 | 자동 재요청 |
|---|---|---|
| 조회 중 | 최초 skeleton, 재조회는 기존 내용과 갱신 중 표시 | 이전 요청 취소·새 요청 1회 |
| 401 | 보호 데이터·초안 지우기, 로그인 이동 | 없음 |
| 403 FORBIDDEN | 권한 재확인, 제한 동작 비활성화 | 필요한 GET만 |
| 404 프로젝트 | 접근 불가 안내, 내용·초안 제거 | 없음 |
| 404 업무 | 상세 종료·목록 링크, 다른 업무 데이터는 유지 | 목록 GET 가능 |
| 409 | 초안 보존, 충돌 비교 UI | 최신 조회만 |
| 422 | 필드 오류와 첫 오류 포커스 | 없음 |
| 네트워크·503 | 기존 데이터·초안 유지, 다시 시도 | 쓰기 자동 재시도 없음 |
| 429 | 제한 안내, 서버 헤더가 있으면 대기 시간 표시 | 없음 |

업무 페이지가 열린 채로 날짜가 바뀔 수 있다. 탭이 다시 활성화될 때와 사용자가 ‘새로고침’을 누를 때 현재 데이터를 다시 조회한다. 장시간 foreground 상태라면 Asia/Seoul 날짜 변경을 확인해 GET을 한 번 실행한다. 지속적인 폴링·실시간 push는 사용하지 않는다.

클라이언트 요청 제한 시간은 15초다. GET timeout은 취소와 재시도 버튼을 제공한다. mutation timeout은 서버 완료 여부가 불명확하므로 실패가 확정된 것처럼 ‘저장 안 됨’이라고 단정하지 않는다. 성공 여부를 목록·상세에서 확인하게 한다.

## 12. 테스트 전략

### 12.1 계층별 책임

| 계층 | 도구 | 검증 대상 | 배제할 중복 |
|---|---|---|---|
| 규칙 단위 | pytest | 날짜·상태·필드 합성·권한 판단 | ORM 메서드 호출 횟수만 검증하는 테스트 |
| API·DB 통합 | pytest + FastAPI 클라이언트 + PostgreSQL | 인증·권한·제약·트랜잭션·동시성 | PostgreSQL 규칙을 SQLite로 대체 |
| 프론트 컴포넌트 | Vitest + Vue Test Utils | 입력·오류·권한 버튼·충돌·응답 순서 | 스타일 클래스명만 비교 |

| 정적 검사·빌드 | Ruff, Python 타입 검사, vue-tsc, ESLint, Vite build | 타입·구문·빌드 회귀 | 빌드 성공만으로 기능 완료 주장 |

통합 테스트는 전용 PostgreSQL DB에서 실행한다. DB 이름·APP_ENV가 test 조건인지 확인하는 보호 장치를 둔다. 마이그레이션을 실제 적용하고 테스트별 데이터를 격리한다. 커밋·복합 FK·잠금 테스트는 외부 트랜잭션 rollback으로 숨기지 않고 독립 연결의 실제 commit으로 검증한다.

날짜·시각은 서비스가 호출하는 Clock 인터페이스 또는 작은 주입 가능한 함수로 고정한다. 7일을 실제로 기다리거나 자정에만 통과하는 테스트를 만들지 않는다. 동시성은 독립 DB 연결 두 개와 동기화 barrier로 재현하고 임의 sleep에만 의존하지 않는다.

### 12.6 핵심 E2E 시나리오

**E2E-01 팀 협업:** A 가입·로그인 → 프로젝트 생성 → B 별도 브라우저에서 가입 → A가 B 추가 → A가 B 담당 업무 생성 → B 목록 확인·진행 중 변경 → A 새로고침 후 결과 확인.

**E2E-02 접근 격리:** C 브라우저로 프로젝트·업무 URL 직접 진입 → 접근 불가 → API 직접 호출도 404 → A/B 정보가 화면·응답에 없음.

**E2E-03 충돌:** A와 B가 같은 업무 편집 → A 저장 → B 저장 충돌 → B 초안 유지 → 최신 값 비교 후 B가 명시적으로 일부 변경 저장.

**E2E-04 권한 변경:** A가 B에게 소유권 이전 → A의 설정 버튼 제거 → A의 소유자 API 요청 403 → B가 A를 제거 → A 담당 업무 미배정·작성 업무 유지 → A 재접근 404.

**E2E-05 삭제·지속성:** 새로고침·API 재시작 후 프로젝트 확인 → 소유자가 이름 확인 후 삭제 → 프로젝트 목록과 DB에서 제거 → 다른 프로젝트는 유지.

테스트 계정은 브라우저 context별로 격리하고 production 계정을 사용하지 않는다. 일반 기능 E2E는 테스트 프록시의 완화된 제한으로 실행하고 AU-14는 실제 5회/분 정책의 독립 프록시 환경에서 따로 검증한다. 테스트용 완화 설정이 production에 적용되지 않음을 설정 테스트로 확인한다.

## 14. 포트폴리오 시연 순서

1. 새 계정으로 로그인하고 빈 프로젝트 목록에서 프로젝트를 만든다.
2. 팀원을 추가하고 담당자를 지정한 업무를 생성한다.
3. 상태 보드에서 업무를 진행 중·완료로 바꾸고 전체 완료율을 확인한다.
4. 검색·담당자·지연 필터를 조합한다.
5. 비소속 계정의 접근 차단을 보여준다.
6. 두 브라우저의 수정 충돌과 수동 재적용을 보여준다.
7. 소유권 이전·팀원 제거 후 담당자 해제와 권한 변경을 보여준다.
8. 원본 대비 데이터·권한·오류·검증 설계가 어떻게 달라졌는지 설명한다.

시연 순서는 개발 작업 순서나 일정 추정이 아니다. 실제 구현 계획은 세 설계 문서 검토 이후 작성한다.
